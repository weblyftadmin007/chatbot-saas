    1. The Big Picture (5 min read)

    You're going to build a robot helper that lives on websites. Picture a little robot that pops up in the corner of a business's website and says "Hi! How can I help you?" It does four things for that business, 24 hours a day, 7 days a week:

    • 💬 Chats with visitors — answers questions instantly, even at 2 AM
    • 📅 Books appointments — a visitor says "Book Tuesday at 2pm" and it actually books it
    • 📖 Answers from the business's own info — you upload their FAQ PDF and the robot answers from that, not from thin air
    • 📧 Sends confirmation emails — bookings trigger automatic confirmation emails (Chapter 6 explains the one caveat about how the customer's real address is captured)

    And here's the business model: you sell this to local businesses — dentists, hair salons, plumbers, tutors, consultants, auto shops. They pay you a monthly subscription. You manage every client from one control panel. One robot brain, many clients, each with their own name, colors, and info. That's what "SaaS" means: Software as a Service — one software, many customers paying monthly.

    • Google Apps Script turns your existing Gmail into an email API. Every email service (SendGrid, Resend) needs a credit card and a verified domain; Gmail is already verified.

    3. How It Works (3 min read)

    Zero jargon version. When a visitor types a message on a client's website, here's the whole journey — under 3 seconds:

    flowchart LR
    A["👤 Visitor types
    'Book Tuesday 2pm'"] --> B["💬 Chat widget
    on the business's site"]
    B --> C["🌐 Checkpoint
    (rate limit + security)"]
    C --> D["🧠 AI brain
    understands + decides"]
    D --> E["🗄️ Filing cabinet
    checks the calendar"]
    E --> F["📧 Auto emails
    to customer + business"]
    F --> A
    1. The visitor types. The chat bubble on the website captures the message.
    2. The checkpoint. The message passes through a security gate (nginx on the AI's host) that limits how fast anyone can spam and checks the request is legit.
    3. The AI brain understands. A small AI model figures out what the visitor wants — booking, a question, or a human. It can do this because it was "shown" examples during setup.
    4. The filing cabinet checks. For questions, it searches the business's uploaded PDF by meaning, not keywords. For bookings, it checks the business hours and existing appointments and picks open slots.
    5. Emails fly out. Google Apps Script sends the confirmation to the customer and a heads-up to the business.

    The whole thing costs $0/month because: the AI runs on the Gemini API free tier (called by a Cloudflare Worker — Hugging Face's Docker hosting is no longer free, so the backend moved to Cloudflare), the data sits in Turso's free database, the widget and dashboard are served by Cloudflare Pages' free network, the emails go through your free Gmail, and the logins use Clerk's free tier. The only thing you pay is attention.

    Restaurant analogy. The widget is the waiter taking orders. The AI brain is the chef who decides what dish to cook. The database is the reservation book and recipe box. Apps Script is the mailroom. You're the restaurant owner — you set the menu (upload the PDF), the hours, and the prices. The customers never see the kitchen.

    4. Week 1: Foundation (Day by Day)

    This week is all accounts, secrets, and deploys. It's the most clicky week — 2–3 hours total. Work through it in order; every day ends in a test you can see pass, so you always know it worked.

    Day 1 — Create the 6 accounts (45 min)

    Exactly what to click is in Chapter 2. By the end of Day 1 you should have:

    • GitHub account, logged in
    • Hugging Face account + HF_TOKEN (starts hf_) saved
    • Turso database chatbot-db + URL + token saved
    • Clerk app + pk_test_... and sk_test_... saved, your email allowlisted
    • Cloudflare Account ID + API token saved
    • Google Apps Script project with Code.gs pasted, deployed as web app, URL saved, testEmail() run once (check your Gmail!)

    How to know it worked: you have 8 saved values in your notes file and a test email in your inbox.

    Day 2 — Get the code and add the 11 secrets (30 min)

    You need a copy of this project on GitHub under your account. If you have a template repo link, click Use this template → name it (e.g. my-chatbot-saas) → create. If you already have the repo, skip.

    Now add the secrets. On your GitHub repo page: Settings → Secrets and variables → Actions → New repository secret. Add these 11, one by one (copy each from your notes file):

    Secret name (exact)Value from
    TURSO_DATABASE_URLTurso connection details (starts libsql://)
    TURSO_AUTH_TOKENTurso connection details
    CLERK_PUBLISHABLE_KEYClerk → API Keys (starts pk_test_)
    CLERK_SECRET_KEYClerk → API Keys (starts sk_test_)
    GAS_WEBAPP_URLApps Script deploy URL (ends /exec)
    GEMINI_API_KEYGoogle AI Studio key (replaces the old local model — chat + embeddings run on Gemini)
    ADMIN_EMAILSYour email(s), comma-separated — allowed on /admin/* (must match your Clerk allowlist)
    ADMIN_BOOTSTRAP_TOKENOptional long random string — only for the first tenant/knowledge uploads (delete once the dashboard works, Phase 3)
    CLOUDFLARE_API_TOKENCloudflare API token
    CLOUDFLARE_ACCOUNT_IDCloudflare dashboard → Account ID
    ADMIN_EMAILYour email (must match your Clerk allowlist)

    How to know it worked: the secrets page lists all the names with no typos. Secrets are hidden after saving — that's normal. If you typo one, delete and re-add it.

    Day 3 — Deploy the AI backend to Cloudflare Workers (30 min)

    1. Set the GitHub secrets from Chapter 2 — especially TURSO_DATABASE_URL, TURSO_AUTH_TOKEN, GEMINI_API_KEY, CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID. (No Hugging Face accounts or Space names needed anymore.)
    2. Create the Turso database if you haven't: turso db create chatbot-db.
    3. Push anything to main in your GitHub repo (or run the Deploy Chatbot API Worker to Cloudflare workflow manually: Actions → Deploy Chatbot API Worker → Run workflow). The workflow typechecks worker/, deploys with wrangler, and writes the Worker secrets.
    4. Wait ~1–3 minutes (no AI models to download — the model lives in the Gemini API). The Actions tab shows progress.

    How to know it worked: open https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/health in a browser (run npx wrangler whoami locally to see your subdomain). You should see {"status":"healthy","version":"1.0.0",...}. Workers don't sleep, so no keep-alive is needed — but watch Gemini's daily free quota (Chapter 9 troubleshooting).

    Where things stand (September 2026). The repo you're cloning is mid-migration from the old Hugging Face Docker backend to the Cloudflare Worker stack. What's implemented now (Phase 1): widget chat with RAG answers, knowledge upload (text/FAQ), conversation history, and Worker deploys via GitHub Actions. What's still being ported (Phases 2–4): appointment booking + emails, the full admin dashboard, PDF upload, and the legacy scripts/. The old Python backend lives on in backend/ as the reference implementation. The Appendix at the end of this guide spells out the phases in detail.

    Day 4 — Set up the database (15 min)

    1. Create the database (one time): turso db create chatbot-db.
    2. Load the schema — the Worker needs the tables to exist before anything works (idempotent — safe to re-run): 
      turso db shell chatbot-db < worker/db/schema.sql
      This creates the 7 tables. Embeddings are stored in knowledge_chunks as float32 BLOBs and ranked inside the Worker (no DB vector extension needed). No model downloads — embeddings run on the Gemini API.
    3. Copy the connection URL + auth token (turso db show chatbot-db) into the GitHub secrets TURSO_DATABASE_URL / TURSO_AUTH_TOKEN, then re-run the Day 3 deploy workflow.

    How to know it worked: in Turso's dashboard → your database → Explore/SQL, run SELECT name FROM sqlite_master WHERE type='table'; — you should see 7 tables: appointments, conversations, end_users, knowledge_chunks, messages, tenants, usage_logs.

    Day 5 — Deploy the widget and admin (25 min)

    1. Cloudflare dashboard → Workers & Pages → Create → Pages → Connect to Git → pick your repo.
    2. Project name: chatbot-widget → Production branch: main → Framework: none → Build command: cd widget && npm run build → Build output directory: widget/dist → Save and Deploy.
    3. Repeat for chatbot-admin with build command cd admin-dashboard && npm run build and output admin-dashboard/dist.
    4. Give the admin build your Clerk key. The admin app bakes its Clerk publishable key in at build time. In the chatbot-admin Pages project go to Settings → Environment variables → add VITE_CLERK_PUBLISHABLE_KEY = the pk_test_… value from your notes → Save → redeploy. (If you deploy via GitHub Actions instead of the Pages git integration, add the same variable to the npm run build step of .github/workflows/deploy-admin.yml.) Without it the admin page loads but the login screen never appears.
    5. Then push to main (or trigger the workflows) to build them via GitHub Actions instead — pick one path (Pages git integration or Actions) to avoid double deploys.

    How to know it worked: visit https://chatbot-widget.YOUR-SUBDOMAIN.pages.dev/widget.js — you should download a JS file (the build emits exactly this filename). Visit https://chatbot-admin.YOUR-SUBDOMAIN.pages.dev — you should see a login screen (Clerk). The dashboard is fully wired once the key above is set: tenant CRUD, conversations, appointments, knowledge upload, and settings save all go through the admin API with your session token attached automatically.

    Week 1 done = skeleton standing. You now have: a live AI brain with a database, a downloadable widget, and a login screen. Nothing is "yours" yet — Week 2 teaches the brain.

    5. Week 2: Teaching the Brain

    Now the robot learns its first real job. You'll feed it a client's information (a PDF), let it read the business hours, and test that it answers correctly. ~1 hour this week.

    Day 1 — Create your first tenant (15 min)

    A tenant is a client — one business with its own robot personality. In the Space terminal (you did the Day-3 Dockerfile extra from Week 1, right? These commands need it):

    python scripts/create_tenant.py --name "Weblyft Design" --slug weblyft-design --color "#3B82F6"

    --slug is the robot's address: lowercase letters, numbers, and hyphens only. It becomes part of the install code, so pick something clean (weblyft-design, not Weblyft Design!!!).

    How to know it worked: the script prints the tenant's ID and a ready-made embed code. Or check Turso: SELECT slug, name FROM tenants;

    Day 2 — Upload the client's brain food (15 min)

    Ask your client for their FAQ, services list, price list, or about page — anything with facts they want the robot to know. Put it in a PDF (or plain text). Then:

    python scripts/upload_knowledge.py --tenant weblyft-design --file faq.pdf

    What happens inside (plain version): the PDF is read, chopped into ~500-word bite-size pieces, each piece is turned into a "meaning fingerprint" (a list of 768 numbers — an embedding), and all of it is filed in the database. Later, when a visitor asks something, the robot fingerprints their question too and pulls the pieces whose fingerprints are most similar.

    How to know it worked: the script prints Created N chunks from M characters. In Turso: SELECT COUNT(*) FROM knowledge_chunks WHERE tenant_id = (SELECT id FROM tenants WHERE slug='weblyft-design');

    Day 3 — Teach it the business hours (10 min)

    python scripts/extract_business_hours.py --tenant weblyft-design --file faq.pdf

    The AI reads the PDF itself, finds the opening hours, and saves them as the client's calendar rules. (If your PDF has no hours, skip this — the robot defaults to Mon–Fri 9–5, which you can change later in the dashboard.)

    How to know it worked: the script prints the hours JSON it found. Verify in Turso: SELECT business_hours FROM tenants WHERE slug='weblyft-design';

    Day 4 — Test questions (20 min)

    Test the robot exactly like a customer would. In the Space terminal (or any terminal with curl):

    curl -X POST "https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/chat/weblyft-design" \\
  -H "Content-Type: application/json" \\
  -d '{"message": "What are your hours?", "session_id": "test123"}'
    You typeExpected behavior
    "What are your hours?"Answers from the uploaded PDF — the exact hours, not a guess
    "Book an appointment for tomorrow 2pm"Checks the calendar, confirms the booking, streams a confirmation
    "What times are open Friday?"Shows available slots
    "Do you offer refunds?"Answers from the PDF, or honestly says it doesn't know (never makes it up)
    "Talk to a human"Polite handoff message

    How to know it worked: each answer makes sense and the streamed text arrives in pieces. If an answer is wrong, re-check the PDF's wording — the robot can only know what the PDF says.

    Day 5 — Polish (15 min)

    • Try weird phrasings: "can I come in on saturday?", "book me in" — the robot should still route them correctly (it was trained on examples like this).
    • If something keeps misclassifying (e.g. "book" triggers a general answer), add the exact phrase to the few-shot examples in backend/app/services/llm.py and redeploy — the deep-dive guide explains how.
    • Re-upload a cleaner PDF if answers are vague. Better input = better robot.
    The "how to know it worked" habit. Every step in this guide has a checkable result. When you're running a business on this, that habit is what saves you: change one thing, verify one thing, move on. Never change three things and hope.

    6. Week 3: Appointments & the Widget

    Week 3 makes the robot visible and useful: real booking emails, then the chat button on a real website. ~2 hours.

    Day 1 — Make sure email actually sends (20 min)

    You already deployed the email robot in Week 1. Now prove it end to end. Easiest: open your Apps Script project → run the testEmail function → check your inbox. If you did the Day-3 Dockerfile extra, you can also use the terminal version — in the Space terminal:

    python scripts/test_gas_email.py --to your@email.com

    How to know it worked: you get ✓ Email sent successfully! and the test email lands in your inbox within seconds. If it fails, check: the GAS_WEBAPP_URL secret is the /exec URL, the deployment is "Anyone" + "Execute as me", and you ran testEmail() once in Apps Script to authorize.

    Day 2 — Test a real booking (20 min)

    Chat with your own robot like a customer:

    curl -X POST "https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/chat/weblyft-design" \\
  -H "Content-Type: application/json" \\
  -d '{"message": "Book an appointment for tomorrow at 2pm", "session_id": "test-booking"}'

    Then check Turso — an appointment row should exist:

    SELECT start_time, end_time, status FROM appointments;

    How to know it worked: the chat confirms the booking and a new row appears when you re-run the appointments query. Book a second appointment at the same time — the robot should refuse it and offer alternatives (that's the conflict check doing its job). On the email front, read the quirk right below: the chat path sends its confirmation to a placeholder address, so a real email only goes out when you use the dedicated booking endpoint with the visitor's actual email.

    One known quirk in the current code. The chat-based booking sends its confirmation email to a placeholder address (customer@example.com), while the dedicated booking endpoint (POST /widget/appointments/{slug}) emails the real customer address you pass in the request. For production, capture the visitor's email in the widget (a tiny "what's your email?" step) and pass it through — the deep-dive guide flags this in Chapter 12.

    Day 3 — Build and deploy the widget (20 min)

    If you set up Cloudflare Pages in Week 1, the widget is already deployed. Get your widget URL:

    https://chatbot-widget.YOUR-SUBDOMAIN.pages.dev/widget.js

    Test it on a scratch page — create any HTML file with this one line before </body>:

    <script src="https://chatbot-widget.YOUR-SUBDOMAIN.pages.dev/widget.js" data-tenant="weblyft-design"></script>

    Open the file in a browser. How to know it worked: a floating chat button appears bottom-right, in the client's color, and clicking it opens the chat with the greeting you set.

    Day 4 — Install it on the client's site (15 min)

    Send the client one instruction — or better, do it with them on a call:

    1. Open their website's HTML (WordPress: Appearance → Theme File Editor → footer.php; or their developer pastes it in the site template).
    2. Paste the one-line script tag just before the closing </body> tag.
    3. Save and refresh the site.

    How to know it worked: the button appears on their live site. Test on their phone too — the widget is responsive and the booking flow works on mobile (Chapter 6 of the deep-dive explains the mobile slot picker).

    Day 5 — Pilot polish (30 min)

    • Book from a phone browser (Safari/Chrome) — slots should be tappable.
    • Test the "closed day" case: ask for Sunday — no slots should appear.
    • Test the timezone case: if the business is in New York, make sure timezone is America/New_York on the tenant (dashboard → Settings tab, or a quick SQL update).
    • Take a screenshot of the working widget on their site — you'll use it in your pitch for client #2.
    Week 3 done = the product exists. A business's website now has a 24/7 receptionist that books real appointments and emails confirmations. You have proof for the next sale.

    7. Week 4: Your Dashboard & Launch

    This week you take the wheel: the admin dashboard, your first real client, monitoring, and the launch checklist. ~1.5 hours.

    Day 1 — Log in and look around (20 min)

    Open https://chatbot-admin.YOUR-SUBDOMAIN.pages.dev → sign in with Clerk (use the email you allowlisted — if you get "couldn't sign you in", add the admin URL to Clerk → Domains and allowed redirect URLs).

    Tour the screens:

    • Tenants — your client list. Click one to open its detail page.
    • Overview tab — conversations, appointments, confirmed vs pending counts.
    • Conversations tab — every chat thread with its last message.
    • Appointments tab — every booking with date, time, status.
    • Knowledge tab — upload a client's PDF/TXT from the browser (note: this page still needs its auth wiring, so if an upload fails, use the Week 2 terminal commands instead — they do the same job).
    • Settings tab — the business-hours editor (timezone, slot length, buffer) — saving from here is still being wired up, so until then set hours with the Week 2 extraction command or the SQL in Chapter 10).
    • Analytics — platform totals and your busiest clients.
    Honest status of the dashboard. Sign-in works once the Week-1, Day-5 key is set, but in the current code the data screens need two wiring steps that aren't finished: the admin app must attach your Clerk session token to its API calls, and its page layout must mount the routes. Until those land, lists can stay empty even right after a successful login — that's a known code gap, not something you did wrong. The terminal recipes from Weeks 2–3 (create tenant, upload PDF, extract hours, test booking) do exactly the same jobs and work today, so lean on them while the dashboard catches up.

    Day 2 — Add your first real client (20 min)

    The 5-minute client recipe, dashboard edition:

    1. Tenants → Add Tenant → name (e.g. "Bob's Plumbing"), slug (bobs-plumbing) → Create. (Heads-up: the dashboard's color picker is buggy — the chosen color won't stick. Set the color from the terminal instead: python scripts/create_tenant.py --name "Bob's Plumbing" --slug bobs-plumbing --color "#10B981" if you're creating it that way, or patch it later with SQL.)
    2. Upload their FAQ PDF with the Week 2 command (Day 2), using their slug: python scripts/upload_knowledge.py --tenant bobs-plumbing --file faq.pdf.
    3. Set their timezone and hours in the dashboard (Tenant → Settings tab saves hours/timezone/slot duration/buffer directly), or re-run the extraction command (Week 2, Day 3) with their slug.
    4. Copy the embed code (Week 3, Day 3) → email it to the client with one instruction: "paste before </body>" — or offer to do it on a 10-minute call.
    5. Test their robot: "What are your hours?" and "Book for Friday 10am".

    Day 3 — Set up monitoring (20 min)

    Free uptime checks so you know before your client does:

    • No keep-alive needed: Cloudflare Workers don't sleep, so the old 30-minute keep-alive workflow is gone. Monitor request counts + Gemini quota instead (Cloudflare dashboard → Workers → chatbot-api).
    • Uptime Kuma (free, or a hosted instance): add a monitor for https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/health every 60 s, with notifications to Telegram/email. You'll get the ping when it's down. Workers don't sleep, so any outage is a real one.
    • Email quota: in Apps Script, run checkQuota() occasionally — it prints how many emails you have left today.

    Day 4 — Launch checklist (30 min)

    At ~15 clients the support load becomes real.     9. Troubleshooting — Top 20

    "If X happens, do Y." These cover everything a non-technical operator is likely to hit. When in doubt, the health check tells you which half of the world is broken:

    Open: https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/health
→ "healthy" = your system is fine, the problem is on the site/browser side
→ error/timeout = your system is waking up or down, check the Space dashboard
    #If this happens……do this
    1Widget button doesn't appear on the client's siteCheck the script tag is exactly <script src="https://chatbot-widget.YOUR-SUBDOMAIN.pages.dev/widget.js" data-tenant="their-slug"></script>, before </body>. Open the site, press F12 → Console — any red errors point to the cause (CSP, wrong slug, blocked script).
    2Button appears, chat says "Failed to fetch"The widget's server calls are being blocked — usually the site's security policy (CSP) or the Space is asleep. Wait 30 s and retry; check the site's CSP needs the Space origin allowed.
    3First message takes 30+ secondsThe Space was asleep (free tier). It wakes itself. Tell clients this happens once after long quiet periods; the keep-alive pinger prevents it in practice.
    4Bot gives wrong answersIt only knows what's in the PDF. Re-upload a better PDF (clearer, correct facts), then re-test. Wrong hours → re-run the hours extraction or fix them in Settings.
    5Bot says "I don't have that information" for something you uploadedThe question's meaning didn't match any chunk closely enough. Rephrase the PDF section to use the words customers use, or upload an FAQ with the exact Q&A.
    6No appointment slots ever showBusiness hours are missing/closed for those days. Check tenant → Settings → hours + timezone. Closed days (empty open/close) show nothing — that's correct behavior.
    7Slots show but booking says "no longer available"Someone else booked it milliseconds before (or it's in the past). Refresh — that's the conflict check protecting the calendar. Test by booking the same slot twice yourself.
    8Times are off by hoursTimezone mismatch. The tenant's timezone must match the business's location (Settings tab). Check it before blaming the calendar.
    9Booking succeeds but no email arrivesCheck your Gmail Sent folder first (all sends go through your Gmail). Then run python scripts/test_gas_email.py --to your@email.com in the Space terminal. If that fails, re-deploy the Apps Script and run testEmail() to re-authorize. Remember the 100/day limit.
    10Emails land in spamRecipients click "not spam". Gmail→Gmail is usually fine. Keep email subject lines normal (no "FREE!!!").
    11Client says chat history disappearedA refresh with private/incognito browsing loses the session (localStorage). Normal — a new thread starts. Not a data loss bug.
    12Admin login loopsClerk doesn't know your admin URL yet. Add chatbot-admin.YOUR-SUBDOMAIN.pages.dev to Clerk → Domains and allowed redirect URLs. Also confirm your email is in the allowlist.
    13Logged in but dashboard errors / empty listsUsually the admin page can't reach the backend (network) or the auth token isn't attached. Check the browser console for 401/403 and verify your email = ADMIN_EMAIL secret.
    14"Tenant not found" when testingSlug typo (case matters) or the tenant was created in a different database than the one the Space uses. Check Turso: SELECT slug FROM tenants;.
    15Uploaded PDF does nothingThe script must print "Created N chunks". If it errors, the file path was wrong or the tenant slug was wrong. If it succeeds but the bot still doesn't know things, the PDF was scanned images (no text) — convert it to real text first.
    16Everything was working, now the health URL is downSpace crashed or hit a quota. Check the Space page (it shows a red/green pulse), open the terminal, look at tail /var/log/supervisor/fastapi_err.log. Restart the Space from the dashboard if needed. (Both …/health and …/widget/health are served by the app.)
    17Chat works, but answers take 10 s even when awakeCPU inference is just slow on the free tier. Normal. Keep answers short (max_tokens caps already help), and consider a paid GPU upgrade when clients complain.
    18New client's widget shows the OLD client's colors/greetingYou copied the embed code with the wrong data-tenant slug. Check the slug on the client's page matches their tenant exactly.
    19Bot books appointments for closed daysBusiness hours JSON is missing or the tenant timezone is wrong. Set both in Settings. If it persists, re-run the hours extraction.
    20You changed something, deployed, and nothing changedDeploys are async. Check the Actions tab for the workflow run to finish (green). Then hard-refresh the page (Cmd+Shift+R). Then test.
    When to ask for help: if the health URL is healthy but you're stuck for 30+ minutes, or you see errors you don't understand in a log — that's the moment to open the deep-dive guide (its Chapter 12 has root-cause analysis for every one of these) or ask a developer friend with this repo open. Don't Google-fix production by trial and error.

    Key decisions locked in the spec

    • LLM: Gemini free tier (flash-class chat model set via CHAT_MODEL; gemini-embedding-001 @ 768 dims, matching the float32 BLOBs in knowledge_chunks). Groq / Workers-AI are optional failovers. Free-tier limits are volatile — verify in AI Studio and treat as config.
