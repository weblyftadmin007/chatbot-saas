    How each day works

    • Goal — one sentence: what "done" looks like.
    • Steps — ordered actions, with exact commands where a command helps.
    • How to know it worked — a concrete test at the end of the day.
    Pacing. A "day" is one focused 30–90-minute session. Skipped a day? Just do the next one — nothing expires. If a day takes far longer than its estimate, stop, note what blocked you, and move on; most "stuck" moments are a typo in a slug, a missing secret, or a deploy still in progress (wait 5–10 minutes before debugging).

    Day 1 — Create Your 6 Free Accounts (60 min)

    Goal: every account exists, and you've saved the credentials you'll need in one place (a notes app, a spreadsheet, or a paper card). No credit card is required anywhere.

    Steps

    1. GitHub — go to github.com, sign up, and enable two-factor authentication (Settings → Password and authentication). You'll host the code here and GitHub Actions will do every deploy for free.
    2. Cloudflare — sign up, then create an API token (My Profile → API Tokens → template “Edit Cloudflare Workers” + Account → Pages:Edit) and copy your Account ID. This replaces Hugging Face: the backend now runs as a Cloudflare Worker, which is free and never sleeps, and your widget + admin dashboard will be served from Cloudflare Pages under this same account. Hugging Face Docker Spaces are no longer free (July 2026).
    3. Google AI Studio — at aistudio.google.com/apikey create a Gemini API key (GEMINI_API_KEY). This replaces the local Ollama model — chat and embeddings run on Gemini's free tier.
    4. Turso (the database) — go to turso.tech, sign up, click Create Database, name it chatbot-db, pick the region closest to your clients. After creation, open the database → Show connection details and copy the Database URL (libsql://…) and the Auth Token.
    5. Clerk (login for your admin dashboard) — go to clerk.com, sign up, create an application named Chatbot Admin. Copy the Publishable Key (pk_test_…) and the Secret Key (sk_test_…). In the Clerk dashboard: Users & Authentication → Email, Phone, Username → enable Email only. Then User & Authentication → Email, Phone, Username → Allowlist → add your email address. (You'll add your admin dashboard domain on Day 4.)
    6. Google Apps Script (sends your emails through Gmail) — go to script.google.com, New Project, delete the default code, paste the whole contents of gas-email/Code.gs from this repo, then Deploy → New deployment → gear icon → type: Web app → Execute as: Me → Who has access: Anyone → Deploy. Copy the Web App URL (it ends in /exec). Finally, run the testEmail() function once in the editor to authorize Gmail access.
    How to know it worked: you have a credentials sheet with exactly these values — TURSO_DATABASE_URL, TURSO_AUTH_TOKEN, GEMINI_API_KEY, CLERK_PUBLISHABLE_KEY, GAS_WEBAPP_URL (Phase 2), ADMIN_EMAILS, ADMIN_BOOTSTRAP_TOKEN (optional), CLOUDFLARE_API_TOKEN, and CLOUDFLARE_ACCOUNT_ID. The test email arrived in your Gmail (if you set up Apps Script).

    Day 2 — Prepare the Repo & Secrets (30 min)

    Goal: the code lives in your GitHub account and all the secrets are stored so the deploy workflows can use them.

    Steps

    1. Open this repository on GitHub and click Use this template → create your own repo (e.g. chatbot-saas) under your account.
    2. Clone it to your machine: 
      git clone https://github.com/YOUR_USERNAME/chatbot-saas.git
cd chatbot-saas
    3. Go to your repo → Settings → Secrets and variables → Actions → New repository secret, and add the values from Day 1. The exact secret names are required — copy them precisely: 
      TURSO_DATABASE_URL
TURSO_AUTH_TOKEN
GEMINI_API_KEY
CLERK_PUBLISHABLE_KEY
ADMIN_EMAILS
ADMIN_BOOTSTRAP_TOKEN   # optional — first onboarding only (DEPLOY.md §5)
CLOUDFLARE_API_TOKEN
CLOUDFLARE_ACCOUNT_ID
GAS_WEBAPP_URL          # needed in Phase 2
    4. Optional: CLERK_JWKS_URL — only add this if your Clerk key is unusual; normally the Worker derives the token-verification URL from the publishable key automatically.
    How to know it worked: the Actions → Secrets page lists exactly 11 names with no typos. (A typo here is the #1 cause of "works locally, fails in production" — double-check the Turso URL and token especially.)
    Why secrets, not files? The deploy workflows (in .github/workflows/) read these secrets at build time and inject them into the container as environment variables. The app refuses to start without all six backend settings, so missing secrets show up immediately as a failing health check on Day 3.

    Day 3 — Deploy the Backend (45 min, mostly waiting)

    Goal: your AI backend is live on Cloudflare Workers answering the health check; the Turso database has the schema loaded; your Gemini API key is confirmed working.

    Steps

    1. Make sure the GitHub secrets from Day 2 are set (especially TURSO_DATABASE_URL, TURSO_AUTH_TOKEN, GEMINI_API_KEY, CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID).
    2. Push the repo to main (or run the workflow manually): 
      git add -A && git commit -m "Initial deploy" && git push origin main
      This triggers Deploy Chatbot API Worker to Cloudflare — it typechecks worker/, runs wrangler deploy, then writes the Worker secrets. Takes 1–3 minutes. Watch it under the Actions tab.
    3. When the workflow finishes, open the health check: 
      https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/health
      (wrangler whoami shows your subdomain.) You should see {"status":"healthy","version":"1.0.0",...}.
    4. Load the database schema (the Worker talks to Turso over HTTP and needs the tables to exist): 
      turso db shell chatbot-db < worker/db/schema.sql
      Then verify in the Turso dashboard → your database → Explore/SQL: 
      SELECT name FROM sqlite_master WHERE type='table' ORDER BY name;
      You should see 7 tables: appointments, conversations, end_users, knowledge_chunks, messages, tenants, usage_logs.
    5. Confirm your Gemini key works. No models to download — chat and embeddings run on the Gemini API. In Google AI Studio, confirm the key from Day 1 is valid and note your model's free daily quota (it varies — see the Appendix note on limits).
    How to know it worked: /health returns 200 with healthy; all 7 tables exist in Turso; no model downloads needed.
    Free-tier limits, not cold starts. Workers don't sleep (no keep-alive needed), but the Gemini free tier has daily request caps that vary over time. The Worker handles them gracefully — a friendly “I'm at my usage limit” message instead of an error — and you can add a Groq/Workers-AI fallback later (spec §5.7).

    Day 4 — Deploy Widget & Admin (45 min)

    Goal: the client-facing widget and your admin dashboard are both live on Cloudflare Pages.

    Steps

    1. Cloudflare dashboard → Workers & Pages → Create → Pages → Connect to Git → pick your repo.
    2. Create the widget project: name chatbot-widget, production branch main, framework: None, build command cd widget && npm run build, build output directory widget/dist → Save and Deploy. The build emits exactly widget.js.
    3. Create the admin project: name chatbot-admin, same branch, build command cd admin-dashboard && npm run build, output admin-dashboard/dist → Save and Deploy.
    4. Give the admin build your Clerk key. The admin app bakes the publishable key in at build time. In the chatbot-admin project: Settings → Environment variables → add VITE_CLERK_PUBLISHABLE_KEY = your pk_test_… value → Save → redeploy. Without it the page loads but the login screen never appears.
    5. Tell Clerk about the admin domain. Clerk dashboard → Domains → add chatbot-admin.YOUR-SUBDOMAIN.pages.dev (and your custom domain later). Also add it under User & Authentication → Email, Phone, Username → Allowed redirect URLs.
    6. Verify both URLs:
      • https://chatbot-widget.YOUR-SUBDOMAIN.pages.dev/widget.js — downloads a JavaScript file.
      • https://chatbot-admin.YOUR-SUBDOMAIN.pages.dev — shows the Clerk sign-in screen.
    How to know it worked: widget.js downloads; the admin URL shows a login screen; signing in with your allowlisted email works (you'll see "No tenants yet" — that's correct until Day 8).

    Day 5 — Local Dev Environment (45 min, optional but recommended)

    Goal: you can run and debug the project on your own machine, which makes every later day faster. The database is in the cloud, so "local" means running the API and frontends locally while they talk to the same Turso database.

    Steps

    1. Install Python 3.11+ and Node 20+ (visit python.org and nodejs.org if you don't have them).
    2. Set up the backend: 
      cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
    3. Create backend/.env with the six required settings (the app fails at startup without all of them): 
      TURSO_DATABASE_URL=libsql://your-db.turso.io
TURSO_AUTH_TOKEN=your_token
CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
GAS_WEBAPP_URL=https://script.google.com/macros/s/.../exec
ADMIN_EMAIL=you@example.com
    4. Run the migration from your machine (it's the same remote database): 
      python run_migrations.py
    5. Build the frontends once to prove the toolchain works: 
      cd ../widget && npm install && npm run build
cd ../admin-dashboard && npm install && npm run build
    6. (Optional) Run the API locally: 
      cd ../backend && uvicorn app.main:app --reload --port 8000
      then open http://localhost:8000/health.
    How to know it worked: pip install finishes without errors (the pinned versions resolve — earlier versions of the requirements file did not, which is fixed); run_migrations.py prints the SQL statements it executed; both npm run build commands succeed; localhost:8000/health returns healthy.

    Day 6 — Tour the Codebase (45 min)

    Goal: know where every concern lives, so fixing and extending later is a lookup, not a search.

    Steps

    1. Open the repo in your editor and walk the folder map:
      FolderWhat lives there
      backend/app/api/FastAPI routes: widget.py (public chat/config/availability/appointments/history/health), tenant.py (tenant management, admin-auth-protected), admin.py (platform admin + Clerk JWT verification)
      backend/app/services/llm.py (legacy Ollama client — the new backend calls Gemini in worker/src/llm.ts), rag.py (vector search reference), appointments.py (intents + slots + booking + cancel), knowledge.py (PDF/text/FAQ chunking), email.py (GAS email)
      backend/app/middleware/tenant.pyResolves a tenant from the URL slug, X-Tenant-Slug header, or subdomain
      backend/migrations/001_initial_schema.sql — the whole schema; run by run_migrations.py
      widget/src/The embeddable chat widget (React + Shadow DOM): ChatWidget.tsx, hooks (useChat, useConfig, useSession), components (ChatPanel, SlotPicker, …)
      admin-dashboard/src/Your control panel: pages (Tenants, TenantDetail, Analytics), components (FileUploader, BusinessHoursEditor), and api.ts (attaches your Clerk token to every request)
      scripts/CLI helpers: create_tenant.py, upload_knowledge.py, extract_business_hours.py, test_gas_email.py, seed_demo.py
      gas-email/The Apps Script that turns {to, subject, html} into a Gmail send
      .github/workflows/Auto-deploys (backend → HF, widget + admin → Pages) and the keep-alive pinger
    2. Follow one message end-to-end in backend/app/api/widget.py: the /widget/chat/{slug} handler saves your message, classifies intent, and either runs RAG search + LLM synthesis or the booking flow, then streams the answer back as Server-Sent Events. The widget's useChat.ts reads those events.
    3. Note the files you'll touch most: backend/app/config.py (model names, rate limits), backend/app/schemas.py (default greeting/colors), nginx.conf (rate limits), widget/src/styles.css (widget look).
    How to know it worked: for each question — "where do I change the bot's name?", "where do I add an FAQ?", "where do I change the rate limit?" — you can point at the file without searching.

    Day 7 — Buffer & Your Stack Card (30 min)

    Goal: catch up on anything that slipped, and create the single page that runs your operation.

    Steps

    1. Re-visit any day that wasn't fully green. Most common fixes: a secret typo, a deploy that needed a second run, or models still downloading.
    2. Re-verify the three core URLs in a browser: chatbot-api.YOUR-SUBDOMAIN.workers.dev/health, chatbot-widget.YOUR-SUBDOMAIN.pages.dev/widget.js, chatbot-admin.YOUR-SUBDOMAIN.pages.dev.
    3. Write your Stack Card — one page with: each service, its URL, your login, what it's for, and its free quota. Include the Space terminal path (Settings → Open in terminal) and the two model-pull commands.
    How to know it worked: all three URLs are green, and someone (or you, in a week) could run this operation from the Stack Card alone.

    Day 8 — Create Your First Tenant (30 min)

    Goal: a real (demo) client exists and its branded widget loads on a test page.

    Steps

    1. Open the admin dashboard and sign in. Click Add Tenant and fill in: Business name (e.g. Weblyft Design), Slug (lowercase letters, numbers, hyphens — e.g. weblyft-design), and a Primary Color (this now maps to the widget's primary_color correctly).
    2. Verify the backend knows the tenant: 
      curl https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/config/weblyft-design
      You should get JSON with your name, colors, greeting, and bot name.
    3. Create a test page: a plain HTML file on your computer (or a CodePen) containing the embed line before </body>: 
      <script src="https://chatbot-widget.YOUR-SUBDOMAIN.pages.dev/widget.js" data-tenant="weblyft-design" data-api-url="https://chatbot-api.YOUR-SUBDOMAIN.workers.dev"></script>
    4. Open the test page: a floating button appears bottom-right in your client's color. Click it — the greeting message shows.
    How to know it worked: the config endpoint returns the tenant's brand data, and the floating button + greeting render on your test page.
    CLI alternative. Everything the dashboard does is also available as commands you can run from your machine (the database is remote, so location doesn't matter): 
    python scripts/create_tenant.py --name "Weblyft Design" --slug weblyft-design --color "#3B82F6"
    Note: the legacy Python scripts run against the old backend. On the current stack, create the tenant + upload knowledge with the two curl commands in DEPLOY.md §5 instead.

    Day 9 — Upload Knowledge (45 min)

    Goal: the bot answers questions from the client's own documents, not from thin air.

    Steps

    1. Prepare the client's information. Best sources, in order of usefulness:
      • A FAQ list — exact questions and answers (works best, because retrieval matches question-shaped text).
      • A plain-text or Markdown document of what clients ask about: services, prices, policies, contact info, locations.
      • A PDF — must be real text, not scanned images (a scanned PDF has no text to read).
    2. In the admin dashboard: Tenant → Knowledge tab → upload the file, or choose FAQ (JSON) and paste: 
      [{"question": "What are your hours?", "answer": "Mon–Fri 9am–5pm"},
 {"question": "Do you offer refunds?", "answer": "Yes, full refund if cancelled 24h before"}]
    3. Confirm chunks were created: the Knowledge tab lists the source with a chunk count. Deeper check in Turso: 
      SELECT source_id, COUNT(*) FROM knowledge_chunks
WHERE tenant_id = (SELECT id FROM tenants WHERE slug = 'weblyft-design')
GROUP BY source_id;
    4. Test in the widget: ask a question whose answer is in the document. The bot should answer from it (it streams the answer token by token).
    How to know it worked: the source shows "N chunks", and the widget answers a question that only the uploaded document could answer.
    If it says "I don't have that information": the question didn't match any chunk closely enough (the similarity threshold is 0.7). Rewrite the FAQ using the words customers actually use, or add the exact Q&A pair. If the bot answers but is wordy, that's the temperature setting — fine for now, tune later (Day 20).

    Day 10 — Business Hours & Slots (30 min)

    Goal: the bot knows when the business is open, how long appointments are, and the buffer between them.

    Steps

    1. Admin dashboard → Tenant → Settings tab. Set:
      • Business hours per day (leave closed days empty — the checkbox toggles them).
      • Timezone — the business's location, not yours.
      • Slot duration (15–60 min) and Buffer between appointments.
      Click Save — the Settings tab is fully wired to the API.
    2. Verify the availability endpoint returns sensible slots: 
      curl "https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/availability/weblyft-design?start_date=2026-09-14&end_date=2026-09-20&timezone=UTC"
      Open days should return slots starting on the hour according to open/close times; closed days return none.
    How to know it worked: slots exist only on open days, at the right times for the tenant's timezone, honoring slot duration and buffer.

    Day 11 — Test Every Chat Path (60 min)

    Goal: prove the five intents work, from both the API and the widget UI.

    Steps

    1. Open the widget on your test page and send these messages, one at a time:
      • "What are your hours?" → answer from your knowledge base (general_query + RAG).
      • "What times are open on Friday?" → a list of clickable slots (check_availability).
      • "Book Tuesday at 2pm" → either "booked" or "that slot is taken, here are alternatives" (book_appointment).
      • "Cancel my appointment" → asks for the booking email (cancel_appointment).
      • "Talk to a human" → the handoff message (transfer_human).
    2. When the slot picker appears, click a slot to book, and click the ✕ on the picker (this used to crash — it now dismisses cleanly).
    3. Verify conversation continuity: send a message, refresh the page, and confirm the thread resumes (the widget saves the conversation id to localStorage).
    4. Confirm the API persists everything — get the conversation id from the widget (or the DB), then: 
      curl "https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/history/weblyft-design?conversation_id=REPLACE_ME"
    5. Spot-check with curl for one path: 
      curl -N -X POST "https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/chat/weblyft-design" \
  -H "Content-Type: application/json" \
  -d '{"message": "What are your hours?", "session_id": "test-session-1"}'
      You'll see SSE frames: data: {"type":"content",...} then data: {"type":"done",...}.
    How to know it worked: all five intents produce the expected response, the slot picker books (and closes), a refresh continues the conversation, and the history endpoint returns the messages.

    Day 12 — Emails End to End (45 min)

    Goal: bookings trigger real emails: a confirmation to the customer and a notification to the business.

    Steps

    1. Confirm the Apps Script is authorized and reachable: run testEmail() once more in the Apps Script editor, then from your machine: 
      python scripts/test_gas_email.py --to you@example.com
      Check both your inbox and the Gmail Sent folder.
    2. Set the business notification address. Tenant settings can carry a notification_email; set it in the tenant's settings JSON (via Turso dashboard SQL or a small script): 
      UPDATE tenants SET settings = json_set(settings, '$.notification_email', 'you@example.com')
WHERE slug = 'weblyft-design';
    3. Book an appointment for yourself through the API with your real email: 
      curl -X POST "https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/widget/appointments/weblyft-design" \
  -H "Content-Type: application/json" \
  -d '{"start_time": 1780000000, "end_time": 1780001800, "email": "you@example.com", "name": "Test User", "title": "Consultation"}'
      (Pick start_time/end_time from a slot the availability endpoint returned.)
    4. Verify: you receive the customer confirmation, and the business notification arrives at notification_email.
    How to know it worked: two emails arrive (customer confirmation + business notification) and both appear in Gmail's Sent folder.
    One honest limitation. The chat flow books appointments without collecting the visitor's email, so it only notifies the business (no customer email from chat). The API endpoint above takes an email and emails both parties. If you want customer emails from chat, capture the visitor's email in the widget (a small extension: add an email field / extract it from the message) and pass it to send_appointment_confirmation. Watch the 100-email/day Gmail quota.

    Day 13 — Brand the Widget (30 min)

    Goal: the widget looks like the client's brand on desktop and mobile.

    Steps

    1. In the admin dashboard → Tenant → Settings, confirm: primary color (the button + accents), greeting (the first message), bot name (the header), and optionally logo_url (host the client's logo somewhere public and set it — via the settings JSON or a PATCH).
    2. Verify the config endpoint reflects everything, then hard-refresh the test page. The button, header, and greeting should match the brand.
    3. Test on a phone viewport (DevTools mobile mode or a real phone): the panel fits, the input is usable, the slot picker scrolls.
    4. Confirm continuity again: chat a little, reload — the thread and unread badge behave.
    How to know it worked: the widget matches the brand on desktop and mobile, and a reload continues the conversation.

    Day 14 — Buffer & Onboarding Checklist (30 min)

    Goal: your client onboarding is a written checklist, and you've timed yourself doing it.

    Steps

    1. Write the repeatable checklist (you'll reuse it for every client):
      1. Create tenant (name, slug, color) — dashboard.
      2. Upload knowledge (FAQ/text/PDF) — Knowledge tab.
      3. Set hours, timezone, slot duration, buffer — Settings tab.
      4. Optional: notification_email in settings JSON.
      5. Test chat: general query, availability, booking, cancel.
      6. Give the client the one-line embed code.
    2. Re-run the whole flow for a fresh demo tenant (create one with slug demo or use the seed script) while timing yourself.
    3. Note anything that took longer than expected and fix it now (e.g. prepare a standard FAQ template file you can copy per client).
    How to know it worked: you have a written checklist and a measured time — target under 30 minutes from tenant creation to a live, tested widget.

    Day 15 — Onboard a Second Tenant (45 min)

    Goal: prove the process repeats — two independent clients, isolated data, no cross-talk.

    Steps

    1. Onboard a second tenant end-to-end using your Day-14 checklist. Use a different color, different knowledge (write a small fake FAQ), different hours.
    2. Verify isolation: in the widget for tenant A, ask a question that only tenant B's knowledge knows — tenant A must not answer it.
    3. Verify appointments don't leak: book a slot for tenant A, then check tenant B's availability at the same time — it must still be free.
    4. Time yourself. Compare with Day 14.
    How to know it worked: both tenants work independently — separate colors, separate knowledge, separate calendars — and your onboarding time is close to or under 30 minutes.

    Day 16 — Monitoring & Alerts (45 min)

    Goal: you get told when the site is down — before a client tells you.

    Steps

    1. No keep-alive needed: Cloudflare Workers don't sleep, so the old 30-minute keep-alive workflow is gone. Watch Cloudflare's request counters and your Gemini quota instead (dashboard → Workers → chatbot-api → Analytics).
    2. External uptime monitor: set up a free monitor on https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/health checking every 60 seconds with notifications to Telegram/email. Options: Uptime Kuma (self-hosted, free) or healthchecks.io (free tier). Test the alert by pausing/stopping the Space for a couple of minutes.
    3. Logs: learn where to look when something breaks (Space page → Settings → Open in terminal): 
      tail -f /var/log/supervisor/fastapi_err.log   # the app's errors
# Worker logs: Cloudflare dashboard → Workers → chatbot-api → Logs
tail -f /var/log/nginx/error.log              # rate-limit 503s, 404s
    4. Quotas: Gmail — run checkQuota() in Apps Script (100/day). Turso — dashboard shows reads vs. the 1 B/month free allowance; RAG searches read the most.
    How to know it worked: an alert arrives when the Space is down, keep-alive runs are green, and you know which log to open for each symptom.

    Day 17 — Security Pass (45 min)

    Goal: confirm the fixes from this codebase's hardening hold up: only you can manage tenants, and nothing sensitive is publicly exposed.

    Steps

    1. Tenant API requires auth: call a tenant endpoint with a spoofed slug but no token — it must fail: 
      curl -i -X GET "https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/api/tenants/me" \
  -H "X-Tenant-Slug: weblyft-design"
# → 401 or 403 (HTTPBearer), never tenant data
    2. Admin only for your email: with a valid Clerk token from a different account, admin calls return 403. (Test in the dashboard with a second email if you have one.)
    3. No public model server: confirm https://chatbot-api.YOUR-SUBDOMAIN.workers.dev/ollama/ returns 404 — the nginx proxy was removed.
    4. Apps Script URL stays private: the /exec URL is the only secret protecting your Gmail sends. Don't publish it anywhere; anyone with it can send email as you (up to 100/day).
    5. Secrets hygiene: confirm backend/.env is gitignored and never committed; rotate any key you pasted into a chat or public gist.
    6. Rate limits on: nginx limits the widget endpoints to 30 req/s and API/admin to 60 req/s — a public bot can't hammer your free tier.
    How to know it worked: unauthenticated tenant calls fail, wrong-account tokens get 403, /ollama/ is gone, and your checklist is complete.

    Day 18 — Backup & Recovery (30 min)

    Goal: you can restore everything (database, models, deploys) in under 30 minutes.

    Steps

    1. Back up the database. The simplest full backup is a dump from the Turso dashboard, or with the Turso CLI: 
      turso db shell chatbot-db ".dump" > chatbot-db-backup.sql
      Store it somewhere off-machine (a private GitHub gist, Dropbox, or an encrypted drive). Schedule a weekly reminder to re-dump.
    2. Practice a redeploy. Trigger the "Deploy Chatbot API Worker to Cloudflare" workflow manually (or push a commit touching worker/). When it finishes, confirm /health is green. No model re-downloads — models live in the Gemini API, not the container.
    3. Document restore: write down — restore DB from dump, redeploy, pull models, re-verify health + one chat test.
    How to know it worked: you have a DB dump file, you successfully redeployed, and your written recovery runbook takes under 30 minutes.

    Day 19 — Build Your Sales Kit (60 min)

    Goal: you can pitch and close a client without improvising.

    Steps

    1. Pricing. Pick simple tiers, e.g.:
      TierPriceIncludes
      Starter$49/moChat + answers from their info
      Plus$99/mo+ Appointment booking + email confirmations
      Premium$149/mo+ Custom branding, logo, priority support
    2. One-page proposal. A short document with: what it does (3 bullet points), a screenshot/GIF of your demo widget, pricing, and the 30-second install ("one line of code, we do it for you").
    3. Client install card. A one-pager for the client with their embed line and what to expect in the first week.
    4. Demo video. Record a 2-minute Loom (free) of your demo tenant: ask a question, book an appointment, show the email. Reuse it for every prospect.
    How to know it worked: you can send a complete proposal with pricing, proof (video), and install instructions in under 10 minutes.

    Day 20 — Quality Pass (60 min)

    Goal: your demo is polished enough to show prospects without apologizing.

    Steps

    1. Walk the dashboard as a stranger: create a tenant, upload a file, edit hours, view conversations/appointments — click everything, note anything broken or confusing.
    2. Harden the bot's answers: add the top 10 questions every client of this type asks as FAQ entries (price, hours, location, cancellation, what to bring…). Re-test the previously weak answers.
    3. Check the logs for a day's worth of noise (fastapi_err.log); silence anything repeated.
    4. Optional tuning knobs if answers feel off:
      • Answer too wordy — lower temperature for synthesis in backend/app/services/llm.py (0.2 default).
      • Too many "I don't know" — lower similarity_threshold in rag.py (0.7 default) or improve the FAQ wording.
      • Answers too long — reduce max_tokens (800 default).
    How to know it worked: a friend (non-technical) can open the admin, find things, and get correct answers to the top questions without your help.

    Day 21 — Buffer & Dry-Run (30 min)

    Goal: prove you can onboard a brand-new client in under 30 minutes, live.

    Steps

    1. Create a throwaway tenant (slug like dry-run) and run the whole Day-14 checklist with a stopwatch running: tenant → knowledge → hours → notification email → chat tests → embed line.
    2. Record where time went. Fix the top bottleneck (usually: preparing the FAQ, or re-typing settings).
    3. Delete the throwaway tenant (admin → DELETE sets plan='deleted', hiding it everywhere).
    How to know it worked: full onboarding measured under 30 minutes, with the bottleneck fixed and noted.

    Day 22 — Landing Page & Offer (90 min)

    Goal: one link you can send prospects that sells the service — and demonstrates it.

    Steps

    1. Build a simple one-page site (Carrd, Notion, or a plain HTML file on Cloudflare Pages — all free). Sections: headline ("Never miss a customer again — AI chat + booking for local businesses"), 3 benefits, how it works (3 steps), pricing table, and a call-to-action.
    2. Embed your own widget on the page using your demo tenant's slug — the page literally demonstrates the product. Set a friendly greeting like "Hi! I'm the demo bot — ask me about our services or book a slot."
    3. Make "Book a demo" go through the widget's booking flow (or link to a booking slot on your calendar).
    4. Write the one-line value prop you'll use in every outreach message: e.g. "I set up AI assistants that answer your customers' questions and book appointments 24/7 — first two weeks free, then $X/month."
    How to know it worked: the page is live, the widget works on it, and you have a one-line pitch you're comfortable sending.

    Day 23 — Outreach Day 1 (60 min)

    Goal: 20 businesses on your list, 10 contacted, at least one conversation started.

    Steps

    1. Build the list in a spreadsheet: columns = business name, category, city, contact (email/Instagram/DM), status. Target categories where "missed leads while closed" hurts: dentists, hair/nail salons, plumbers/HVAC, electricians, tutors, consultants, physios, auto shops, restaurants (reservations), real estate agents.
    2. Write one personalized message per business (mention something specific: their reviews, their site, their hours). Keep it short:
      "Hi [Name] — I saw [Business] gets [specific observation]. I build AI chat assistants that answer your customers' questions and book appointments while you're closed — first 2 weeks free, no commitment. Want me to set up a demo on your site?"
    3. Send 10 messages (email or DM). Log statuses in the sheet.
    How to know it worked: 10 messages sent, statuses logged, and at least one reply or "tell me more" in your inbox.
    The pilot offer. Free 2-week pilot (your cost is ~1 hour of setup) removes the risk objection. Convert at the end: "want to keep it on?" Most will say yes at $49–99/mo.

    Day 24 — Outreach Day 2 & Demos (60 min)

    Goal: the list is fully contacted, follow-ups sent, and at least one demo call booked.

    Steps

    1. Send the remaining 10 messages from your list.
    2. Follow up with Day-23 replies (a friendly nudge after 48 h is normal).
    3. Book demo calls. Prep a 5-minute demo script: (1) ask what their top questions/booking pain are, (2) show your live demo tenant answering a question like theirs, (3) show a booking + confirmation email, (4) offer the free pilot with a date to install.
    4. Add a "Follow-up" date column to your sheet and schedule next touchpoints.
    How to know it worked: all 20 contacted, follow-ups sent, and at least one demo call on the calendar (or a clear "no thanks" so you can move on).

    Day 25 — Pilot Kickoff (90 min)

    Goal: your first pilot client is live on their real website.

    Steps

    1. Sign the pilot (a simple one-page agreement: free 2 weeks, then $X/month, 30-day notice to cancel).
    2. Onboard them with your checklist: tenant (their real name/color), knowledge (their real FAQ/PDF — ask for it, or draft it from their site and confirm), hours/timezone/slots, notification_email = their inbox.
    3. Install the widget: either they paste the embed line (give them the exact snippet) or you do it if they'll share a staging page. Verify on the live page: button, colors, greeting, no console errors.
    4. Book a test appointment on their site with your email, confirm both emails arrive, then cancel it in the dashboard (or via the bot).
    How to know it worked: the widget is live on the client's site, answers their real questions, books and emails correctly, and the client knows what happens next (your Day-26 check-in).

    Day 26 — First-Week Check-In (45 min)

    Goal: the pilot is actually working in the wild, and you've captured the client's feedback.

    Steps

    1. In the admin dashboard, review the pilot's conversations and appointments: which questions came in, which booked, any that failed or confused the bot.
    2. Fix the top issues you see: add FAQ entries for questions the bot missed, adjust hours if slots were booked at odd times, re-word anything that read badly.
    3. Call the client. Ask three questions: (1) what did customers use it for? (2) did anything embarrass you? (3) if it was perfect, what would it do next? Log the answers.
    4. Confirm emails are still flowing (their notification inbox).
    How to know it worked: the bot handled real traffic, you fixed what surfaced, and the client can name one concrete win from week one.

    Day 27 — Case Study & Testimonial (45 min)

    Goal: proof you can reuse to close the next clients.

    Steps

    1. Pull numbers from the admin dashboard + Turso: conversations, appointments booked, questions answered, plus anything the client told you ("saved 6 phone calls", "booked while closed").
    2. Take screenshots: the widget on their site, a conversation, a confirmation email.
    3. Write a 200-word case study: who, what they installed, what happened in week one, the quote.
    4. Ask the client for a one-sentence testimonial and permission to use the case study (offer a month at half price or a small credit for it).
    How to know it worked: you have a written case study with real numbers and a client-approved quote you can put on your landing page.

    Day 28 — Business Review (45 min)

    Goal: know your real numbers: revenue, time, and your effective hourly rate.

    Steps

    1. Total the time you spent this month (all sessions, including setup). Be honest — it's usually 25–35 hours.
    2. Total the revenue (pilot, if it converted; otherwise projected). Compute: effective hourly rate = revenue ÷ hours. With a $99/mo pilot and 30 setup hours, month 1 is negative — that's fine; month 2 is where it flips.
    3. Decide pricing for client #2 based on what you now know (don't lower it — raise it if the pilot is happy).
    4. Start the ledger: one row per client with price, hours spent, and monthly revenue. This sheet is the whole business.
    5. Set your next-month target: e.g. 3 clients, $297/mo MRR, 6 h/week.
    How to know it worked: you have real numbers in a ledger, a decision on pricing, and a written next-month target.

    Day 29 — Scale & Automate (60 min)

    Goal: client #3 should take half the time of client #1.

    Steps

    1. Turn your Day-14 checklist into a template document (with a fill-in-the-blank FAQ file you adapt per client).
    2. Automate the boring bits:
      • Standard FAQ template per industry (dental, salon, trades, tutoring…) — copy, edit, upload.
      • A reusable "new client" runbook with the exact commands/URLs (use the Quick Reference chapter below).
      • A weekly 30-minute maintenance slot on your calendar (logs, quotas, one improvement).
    3. Pick the roadmap items that matter next (in rough order):
      1. Email capture in the chat flow (so chat bookings email the customer).
      2. Tenant-owner login (each client manages their own hours/knowledge — sells itself).
      3. Custom domain for each client's widget.
      4. Paid GPU for faster answers when clients complain about speed.
    How to know it worked: onboarding is a copy-paste template, your week has a fixed maintenance slot, and the roadmap has an agreed next item.

    Day 30 — Celebrate & 90-Day Plan (30 min)

    Goal: close the month deliberately and set the next three months on paper.

    Steps

    1. Look back: list the three things that worked (e.g. the pilot offer, the demo video, the checklist) and the three that didn't (e.g. cold emailing, a feature you overbuilt). Keep the winners, drop the losers.
    2. Write the 90-day plan:
      ByTarget
      Day 603 paying clients, $250–300 MRR, onboarding under 20 min
      Day 906–8 clients, $600+ MRR, or a deliberate decision to raise prices / niche down
    3. Schedule the recurring habits: weekly 30-min maintenance, monthly business review, quarterly price review.
    4. Celebrate — you built a real product and launched it at $0 cost. That's the hard part done.
    How to know it worked: you have a written 90-day plan, a maintenance habit on the calendar, and you can honestly name what to repeat and what to stop.

    Appendix — Migration Roadmap: Phases 1–4 in Detail

The project was re-planned around a $0 Cloudflare stack and is being ported in phases (tracked in hf-docker-exit-spec.md). This guide describes the Phase-1 build; the phases below show what ships next.

    Key decisions locked in the spec

    • LLM: Gemini free tier (flash-class chat model set via CHAT_MODEL; gemini-embedding-001 @ 768 dims, matching the float32 BLOBs in knowledge_chunks). Groq / Workers-AI are optional failovers. Free-tier limits are volatile — verify in AI Studio and treat as config.
    • Database: Turso stays. Embeddings live in knowledge_chunks as float32 BLOBs and are ranked inside the Worker (Turso doesn't ship sqlite-vec). Schema: worker/db/schema.sql.
    • PDFs: not parsed in the Worker (free-plan CPU limit) — extracted in the browser or CLI, then uploaded as text (§5.6 of the spec).
    • Auth: Clerk JWKS for /admin/*; optional ADMIN_BOOTSTRAP_TOKEN only for initial onboarding, deleted in Phase 3.
    • Deploys: GitHub Actions → deploy-worker.yml (Worker) + Pages workflows (widget/admin).
